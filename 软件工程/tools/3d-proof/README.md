## 运行和复查

在本目录执行：

```powershell
python server.py --port 19287
```

然后打开[本地试样](http://127.0.0.1:19287/)。本轮使用Codex内置Python 3.12，服务只监听127.0.0.1，端口已登记在全局表。Three.js固定r180，所需模块在vendor/内，保留MIT许可；普通预览不请求CDN。

1. 选择设备详情，拖动实际模型并查看背面/底部；“姿态”滑块改变装配台命名主轴或机器人的夹爪部件。
2. 切流水线查看8个设备实例；切负载查看3个厂房分组、60设备和3000个三维物品标记。负载标记不是Rust引擎已追踪的3000件物品。
3. 选择详细/简化，点击“测量10秒”：预热1.5秒，然后取10秒样本。保持页面可见。CPU为渲染提交耗时；GPU通过WebGL2计时查询取得；帧回调间隔不是显示器实际刷新率或全产品FPS。
4. “保存模型、画面与测量”输出六类完整GLB、当前1920×1080画面和JSON。模型按二进制逐个发送，避免共享2K材质的六个GLB一次性Base64打包超过80MB；此问题已在本轮实际遇到并修正。
5. “重开导出的GLB”从磁盘读取当前设备，重新合批呈现；原始节点、材质与局部变换均保留。
6. “录制设备动作视频”从磁盘加载装配台与机器人GLB，依次呈现主轴往复的整体/近景、夹爪开合的整体/近景，各6秒，输出[24秒MP4](output/device-motion.mp4)与[参数记录](output/device-motion.json)。按动作预览时间逐帧渲染720帧，再由本机FFmpeg编码为1920×1080、H.264、30fps；30fps是视频输出参数。视频已标注尚未接业务仿真，机器人机身保持现有姿态。

视频入口使用已登记的共享FFmpeg 7.1，无新依赖安装。默认路径为`D:/MathModelingTools/envs/cumcm/Lib/site-packages/imageio_ffmpeg/binaries/ffmpeg-win-x86_64-v7.1.exe`；其他机器启动时用`--ffmpeg <实际可执行文件路径>`指定。帧图像顺序送入编码器，不落地720张中间PNG；本地HTTP使用持续连接，修正首轮约第60帧连续上传中断的问题。录制结束后恢复原视图和输入，页面下方可直接播放/下载。

成品约3.76MiB；FFmpeg全段解码确认为24.00秒、720帧、1920×1080、H.264/yuv420p，返回成功；浏览器播放器成功解码并实际播放。关键动作画面见[视频检查图](output/device-motion-contact.png)。

导出的是有完整表面的三角网格、命名部件与材质，不是CAD实体或真实设备尺寸。GLB/Three.js使用Y向上；领域模型X/Y/Z高的转换为`(x,y,z) -> (x,z,-y)`，试样不反写工程数据。

## 对齐目标后的资源预算

纹理算术：一张1K RGBA+mip约5.33MiB；一张2K约21.33MiB。每种设备三张1K图约16MiB；12种独立设备约192MiB。十种1K加两种重点设备2K约288MiB。共享材质/资产时按独立定义计，不按设备实例数量乘。以上是资源估算，不能代替实际峰值显存测试。

原先“普通简模＋两台重点精修”的22—36小时不足以覆盖用户当前指定的整套AI预览精细度。建议将资产与表现部分重新拆成以下规划预算；它替代对应画布/媒体/原生资产工作，不完整叠加到旧166—282小时总量上：

|工作|规划有效工时|
|---|---:|
|统一资产尺寸/坐标/命名/材质与参数化制作入口|4—8|
|6—8类可复用设备主体及适配示例|16—28|

这些仍是规划判断。当前六类试样没有全部达到AI图精细度；不能用本轮脚本生成速度宣称“六类成品资产已完成”或保证后续单台工时。下一次校准应以一个普通设备、一个复杂设备达到目标视觉质量并可接手修改为标准。全产品剩余排期需据此重新分配对应任务，生产与专业内核工量不会因GPU有余量而消失。
