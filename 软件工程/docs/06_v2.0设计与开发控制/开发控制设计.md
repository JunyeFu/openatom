## 3. 关键架构决定：先保留现有Host的生产状态所有权

### 3.1 V2-A01的选择

v2演示沿用现有Windows Native Host持有唯一Engine、物料、资源、事件和接受结果。云端负责设备观测、DaaS查询聚合、会话镜像和指令／回执持久化；由Native内部受管网关actor把设备结果提交到同一Host；两独立设备进程仍经真实云服务互联，普通Agent管道保持隔离。

这个选择满足设备与云端互联，不要求把Tauri、Windows命名管道和整个ProjectHost先搬进云端。现有simulation库可以研究云端运行，但迁移生产内核不是本演示的前置，不在当前设计中同时建设第二个库存或第二个调度提交者。该选择取代上一版需求中尚未实现的“云服务直接持有生产内核”部署假设。

### 3.2 一次生产的责任链

1. 用户在实际工程上确认会话目标、工程修订、设备集合和允许自动调整的范围。
2. Host冻结输入，依据同一Engine检查工艺、物料、端口和资源条件。
3. Host调度产生精确命令；云端按同一命令标识保存并提供给目标设备端。
4. 设备端报告接受、开始、完成或失败；云端保留实际观测和回执，网关提交到原Host。
5. Host核对会话、Job、设备、阶段、命令及当前状态，只让有效回执进入Engine。
6. Engine提交物料与资源变化及接受结果；云端DaaS保存对应确认事件和可查询投影。
7. 工作台、Agent及报告读取该来源；设备停用影响后续未开始工作的选择，回看不发送命令。

设备报告busy不直接写工程资源占用；命令完成数不等于生产接受量。云端持有会话镜像和消息持久化，不取得任意修改Run或库存的权限。

### 3.3 三个必须先解决的具体接点

- 当前Engine.step／boundary按内部虚拟事件推进，start_phase安排阶段动作，finish提交终态。新增外部阶段需明确暂停在哪个边界、等待哪个token及回执，不把私有finish直接公开给网络调用。
- compile::Job已经保存execution、物料location／port、资源及阶段。两设备替代不是修改一个名称：必须确认两设备能力、输入输出位置、角色、单位和资源对应关系，并将选定设备记录到冻结会话的允许路由中。
- ProjectHost目前将普通运行送入execute_engine直到终态。外部等待不能占住UI线程或把旧run_scenario改成另一种含义；需要独立会话及受管工作状态，消费现有权限与关闭保护。

这三项是冻结设计的关键接点；Engine/Host现已实施并有局部实际回执，真实云整链仍按原包剩余动作执行。

## 7. 状态、事务与恢复设计

会话具有草稿、就绪、运行、暂停新派工、待处理、完成及停止等可观察状态。命令具有待接受、已接受、执行中、完成、拒绝、失败及结果待核对状态，状态转移须与实际设备能力一致。

Host先核对条件并建立本次作业的预留，再发布唯一命令；发布结果未知时只查询原CommandId。没有有效完成回执时，不能因工时计时结束就产出；收到重复回执不能重复领料、释放资源或确认接受量。设备停用只改变合法未开始工作，已接受命令须确认撤销或未执行后才能重派。

现有本地预测路径仍按原虚拟时钟推进。外部执行会话使用自己的单一业务时钟和事件顺序；设备时间作为观测信息，不能把晚到旧报文直接回灌成时间倒退。

数据库持久化会话、命令、回执及可查询历史，但不因此承诺当前尚未设计的活跃Engine跨进程自动续跑。Host重启后未知执行保持待核对并查询原命令；恢复设计不得把一个RunResult当作完整的Engine内部运行检查点。

原工程／旧Run按原格式可读。外部会话使用独立ExecutionSnapshot引用冻结输入和实际业务事实，预测Run保持原类型；需要比较时显式对齐来源和观察范围，不把外部结果伪装成完整计算的RunResult。不为v2先给v1所有文件新增必填字段或自动改写历史工程。
